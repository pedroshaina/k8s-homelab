# 11 — Day 2

Short runbooks for running the homelab once it is built. Each change still goes through a pull
request; these are the steps around it.

```bash
export KUBECONFIG=~/.kube/config-homelab TALOSCONFIG=~/.talos/config
```

## Snapshot etcd

etcd holds the whole cluster state, and with one node there is one copy. Snapshot it before any
risky change (upgrades, VM or Talos config changes) to the workstation, never into Git:

```bash
install -d -m 700 ~/homelab-backups
talosctl -e 192.168.1.221 -n 192.168.1.221 etcd snapshot ~/homelab-backups/etcd-$(date +%Y%m%d-%H%M).db
```

**Restore, etcd lost or corrupted but the VM fine:** wipe the node's etcd data, then bootstrap
from the snapshot (use `$HOME`, not `~`: a tilde after `=` is not expanded):

```bash
talosctl -n 192.168.1.221 reset --system-labels-to-wipe EPHEMERAL --reboot --graceful=false
talosctl -n 192.168.1.221 service etcd          # wait for STATE Preparing
talosctl -n 192.168.1.221 bootstrap --recover-from="$HOME/homelab-backups/etcd-<stamp>.db"
```

**Restore, VM or disk lost:** recreate the VM with `infra/tf talos-cluster apply` (lifting
`prevent_destroy` for this recovery only). The machine config comes from the same machine secrets
in the OpenTofu state, which is what makes the snapshot usable. Bootstrap by hand from the
snapshot as above, then `infra/tf talos-cluster configs`. Volumes are separate Proxmox disks and
survive; Argo CD re-converges everything else. Rehearse this on a scratch VM before relying on it.

## Silence alerts during planned work

```bash
kubectl -n monitoring port-forward svc/alertmanager-operated 9093 &
# UI: http://localhost:9093 → New Silence (e.g. alertname=KubeNodeNotReady), or:
curl -XPOST -H 'Content-Type: application/json' http://localhost:9093/api/v2/silences -d '{
  "matchers": [{"name": "alertname", "value": "KubeNodeNotReady", "isRegex": false}],
  "startsAt": "'"$(date -u +%FT%TZ)"'", "endsAt": "'"$(date -u -v+1H +%FT%TZ)"'",
  "createdBy": "me", "comment": "Talos upgrade"}'
```

(`date -v+1H` is macOS; on Linux use `date -u -d '+1 hour' +%FT%TZ`.)

## Upgrade Talos or Kubernetes

One node: the API and every app are down for a few minutes. Before you start: snapshot etcd, run
the checklist in chapter 08, silence the node alerts, and read the release notes of the target
version (Talos supports upgrading one minor version at a time).

**Talos:**

```bash
cd ~/k8s-homelab
SCHEMATIC=$(infra/tf talos-cluster state show talos_image_factory_schematic.this | sed -nE 's/^ *id *= *"([^"]+)".*/\1/p')
talosctl -n 192.168.1.221 upgrade --image factory.talos.dev/installer/$SCHEMATIC:v1.14.2   # the node reboots
```

Then set `talos_version` to the same version in `infra/talos-cluster/terraform.tfvars`, `plan`
(a new image download and an in-place config update; never a VM replacement) and `apply`, so
OpenTofu describes what runs.

**Kubernetes:**

```bash
talosctl -n 192.168.1.221 upgrade-k8s --to 1.37.2
```

Then set `kubernetes_version` in `terraform.tfvars`, `plan` and `apply`. `upgrade-k8s` re-applies
the minimal bootstrap Cilium, so its extra features (L2 announcements, Gateway, Hubble) drop
until Argo CD heals it: `argocd app sync cilium --port-forward --port-forward-namespace argocd
--plaintext`, then `cilium status --wait`.

**Afterwards:** the checklist in chapter 08. If every Argo CD Application shows `Unknown`, delete
the `argocd-repo-server` pod (its Git cache was cut mid-write).

## Bump a chart

Change `targetRevision` in the Application under `platform-gitops/apps/`, read the chart's
release notes, pull request, merge. Argo CD applies it.

**Cilium is special:** its version lives in two places that must match —
`cilium_version` in `k8s-homelab/infra/talos-cluster/terraform.tfvars` (the bootstrap) and
`apps/cilium.yaml` in `platform-gitops` — and nothing checks it. Open both pull requests, merge
`k8s-homelab` first. Preview the platform change against the live cluster before merging, from
the `platform-gitops` checkout:

```bash
r="$(mktemp)"
helm template cilium cilium --repo https://helm.cilium.io \
  --version "$(yq '.spec.sources[] | select(.chart == "cilium") | .targetRevision' apps/cilium.yaml)" \
  --namespace kube-system \
  --kube-version "$(sed -nE 's/^kubernetes_version *= *"([^"]+)".*/\1/p' ~/k8s-homelab/infra/talos-cluster/terraform.tfvars)" \
  -f ~/k8s-homelab/infra/talos-cluster/cilium-values.yaml -f components/cilium/values.yaml > "$r"
yq -i '.metadata.annotations["argocd.argoproj.io/tracking-id"] = "cilium:"
  + ((.apiVersion | select(test("/")) | sub("/.*$"; "")) // "")
  + "/" + .kind + ":" + (.metadata.namespace // "kube-system") + "/" + .metadata.name' "$r"
kubectl diff --server-side --force-conflicts --field-manager=argocd-controller -f "$r"; echo "exit $?"
```

Exit 0 means no change, 1 shows the diff to review, anything higher is an error. Rendering to a
file first matters: a failed render piped into `kubectl` would look like "no changes".

## Add a platform alert

Rules live in `platform-gitops/components/kube-prometheus-stack/rules/platform.yaml`, with
promtool unit tests in `platform.test.yaml` next to it (CI runs them). Write the test first, see
it fail, then add the rule:

```bash
cd ~/platform-gitops/components/kube-prometheus-stack/rules
w="$(mktemp -d)"; yq '.spec' platform.yaml > "$w/platform.yaml"; cp platform.test.yaml "$w/"
(cd "$w" && promtool check rules platform.yaml && promtool test rules platform.test.yaml)
```

Severity `critical` means act now (repeated every 4 h), `warning` means look today (every 24 h),
`info` is never sent.

## Rotate secrets

| Secret | How |
|---|---|
| Any 1Password item read by the cluster | Edit the item, then sync now: `kubectl -n <ns> annotate externalsecret <name> force-sync="$(date +%s)" --overwrite`. Workloads that read it at startup need a restart (`kubectl -n <ns> rollout restart deploy/<name>`): external-dns, cloudflared, Grafana, the Proxmox CSI plugin. cert-manager and Alertmanager pick changes up on their own. |
| A Cloudflare token | Create a new one (chapter 02), update its item or `infra/secrets.sops.yaml` (`proxmox-acme`: then chapter 03 step 4.1–4.2 with production values), delete the old one. |
| The storage driver's Proxmox token | `ssh pve01 'pveum user token remove kubernetes-csi@pve csi'`, then chapter 06 step 3, `force-sync` the `csi-proxmox/config` ExternalSecret and restart `deploy/proxmox-csi-plugin-controller` and `ds/proxmox-csi-plugin-node`. |
| GHCR pull token (yearly) | New classic token (chapter 05), `sops infra/secrets.sops.yaml`, `infra/tf talos-cluster apply` (no reboot), check that a private image still pulls, delete the old token. |
| The release App's private key | Generate a new key in the App settings, `gh secret set RELEASE_APP_PRIVATE_KEY` in every app repository, wait for one release each, then delete the old key. If it leaked: suspend the installation first (that cuts tokens already minted). |
| The 1Password platform token | New token for `k8s-platform-eso`, re-create `bootstrap/platform-1password-svc-acc-token.sops.yaml` (chapter 07 step 2), pull request, re-apply it (chapter 07 step 3.2), revoke the old token. |

Prove a rotation without printing the value — compare a hash before and after:
`kubectl -n <ns> get secret <name> -o json | jq -er --arg k '<key>' '.data[$k]' | shasum -a 256`.

## Break glass

**A Cilium change broke networking.** Argo CD may be unable to repair it: it needs the network to
reach Git and the API.

1. Revert the pull request on GitHub, so Argo CD won't re-apply it later.
2. Re-apply the last known-good Cilium by hand, with the same inputs Argo CD uses:
   ```bash
   git -C ~/k8s-homelab switch main && git -C ~/k8s-homelab pull --ff-only
   cd ~/platform-gitops && git switch main && git pull --ff-only
   helm template cilium cilium --repo https://helm.cilium.io \
       --version "$(yq '.spec.sources[] | select(.chart == "cilium") | .targetRevision' apps/cilium.yaml)" \
       --namespace kube-system \
       -f ~/k8s-homelab/infra/talos-cluster/cilium-values.yaml -f components/cilium/values.yaml \
     | kubectl apply --server-side --force-conflicts --field-manager=argocd-controller -f -
   kubectl -n kube-system rollout restart ds/cilium deploy/cilium-operator
   ```
3. `cilium status --wait`, then the checklist in chapter 08. Argo CD resumes ownership by itself.

**Argo CD itself is broken.** Re-run chapter 07 step 3 from a clean, up-to-date `main` of
`platform-gitops`, including the Helm install even though `argocd-server` exists. If only
`argocd-repo-server` is down, Argo CD can't detect or heal anything, itself included:
`kubectl -n argocd scale deploy argocd-repo-server --replicas=1`.

**The root app is stuck on a sync wave.** A child Application that never becomes Healthy makes
`root` wait at that wave, pinned to that revision: even a revert isn't picked up. Find it, fix the
cause, then end the stuck operation so `root` syncs `main` again:

```bash
kubectl -n argocd get applications                     # which one is not Healthy?
argocd app terminate-op root --port-forward --port-forward-namespace argocd --plaintext
```

A rebuild depends on 1Password: every Application from wave 1 on waits for its
ExternalSecrets. Check `kubectl get clustersecretstore`, `kubectl get externalsecret -A` and the
service account's rate limit.

**The host froze.** The watchdog resets it about 30 seconds after a freeze, so the symptom is an
unexpected reboot. Triage, then the checklist in chapter 08:

```bash
ssh pve01 'journalctl --list-boots | tail -3'          # a boot whose last entry is mid-stream = a freeze
ssh pve01 'journalctl -b -1 -n 30 --no-pager'          # what ran last
ssh pve01 'journalctl -b -1 -k -p err --no-pager'      # kernel errors, machine checks, OOM
ssh pve01 'wdctl; cat /sys/devices/system/cpu/cpufreq/boost'
```
